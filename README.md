# Skating School Platform

Backend-платформа для управления школой фигурного катания. Проект
написан на Java и Spring Boot и предназначен для работы с учениками,
тренерами, услугами, расписанием, бронированиями и оплатами.

Репозиторий содержит два backend-сервиса: **Main Backend** и **Payment
Service**, а также отдельный модуль интеграционных тестов. Сервисы
взаимодействуют через Apache Kafka. Для надёжной публикации событий
используется Transactional Outbox Pattern.

## Архитектура

Проект разделён на два самостоятельных Spring Boot-приложения.

### Main Backend

Основной сервис отвечает за бизнес-логику школы:

- регистрацию, авторизацию и управление пользователями;
- роли `STUDENT`, `TRAINER` и `ADMIN`;
- управление учениками, тренерами и услугами;
- назначение услуг тренерам;
- расписание тренировок;
- создание, просмотр и отмену бронирований;
- обработку результата оплаты и изменение статуса бронирования.

Для защиты от переполнения группы при одновременной записи используется
пессимистическая блокировка PostgreSQL через `PESSIMISTIC_WRITE`.

Redis применяется в Main Backend для кэширования страниц расписания и
данных услуг. При изменении соответствующих данных кэш инвалидируется.

### Payment Service

Отдельный сервис отвечает за обработку платежей:

- принимает запросы на создание платежа;
- хранит платёжные транзакции в собственной PostgreSQL;
- взаимодействует с платёжным шлюзом через интерфейс `PaymentGateway`;
- содержит mock-реализацию шлюза для локальной разработки и
  тестирования;
- обеспечивает идемпотентность обработки платежей;
- защищает операции от гонок при параллельных запросах;
- публикует события о результате обработки платежа;
- содержит механизм сверки статусов платежей.

Payment Service использует собственную базу данных. Redis в этом сервисе
не применяется: кэширование реализовано только в Main Backend.

### Взаимодействие сервисов

Main Backend и Payment Service обмениваются событиями через Apache
Kafka.

Основной сценарий оплаты:

1.  Клиент отправляет запрос на бронирование занятия в Main Backend.
2.  Main Backend создаёт бронирование со статусом `PENDING_PAYMENT` и
    сохраняет событие в outbox в рамках транзакции.
3.  Outbox publisher публикует событие `payments.requested` в Kafka.
4.  Payment Service получает событие и обрабатывает платёж.
5.  Результат обработки сохраняется в базе Payment Service вместе с
    outbox-событием.
6.  Payment Service публикует результат в `payments.completed` или
    `payments.failed`.
7.  Main Backend получает результат и обновляет статус бронирования.

``` text
                    payments.requested
Main Backend  ------------------------------>  Payment Service
     ^                                                |
     |                                                |
     +-----------------------------------------------+
              payments.completed / payments.failed

       PostgreSQL                                  PostgreSQL
       Redis (cache)                               Outbox
       Outbox                                      Mock Gateway
```

Для публикации событий используется **Transactional Outbox Pattern**.
Сервис сначала сохраняет бизнес-изменение и событие в своей базе данных,
а затем отдельный publisher отправляет событие в Kafka. Это снижает риск
потери события между фиксацией транзакции и отправкой сообщения.

Обработка событий учитывает повторную доставку, дубликаты и устаревшие
результаты платежей. Идемпотентность обеспечивается на уровне
бизнес-логики и операций с базой данных.

### Kafka

Kafka используется как брокер событий между сервисами.

Основные топики:

| Топик                | Назначение                   |
|----------------------|------------------------------|
| `payments.requested` | Запрос на обработку платежа  |
| `payments.completed` | Успешная обработка платежа   |
| `payments.failed`    | Неуспешная обработка платежа |

Kafka настроена в режиме **KRaft**, без ZooKeeper. Для аутентификации и
защищённого соединения используется `SASL_SSL` с механизмом
`SCRAM-SHA-512`.

В репозитории есть PowerShell-скрипт `kafka/init-topics.ps1`, который
проверяет подключение к Kafka и создаёт отсутствующие топики.

## Возможности Main Backend

- Регистрация учеников и вход по email и паролю.
- Ролевая модель `STUDENT`, `TRAINER`, `ADMIN`.
- JWT-аутентификация (`HS256`) и хранение паролей в виде BCrypt-хешей.
- Управление учениками, тренерами, услугами и тренировками.
- Назначение услуг тренерам и проверка расписания.
- Поиск, фильтрация, сортировка и пагинация.
- Создание и отмена бронирований.
- Повторное бронирование после отмены.
- Контроль свободных мест при конкурентных запросах.
- Создание бронирования с последующей оплатой.
- Обработка результатов оплаты из Kafka.
- Redis-кэширование расписания и услуг с инвалидацией при изменениях.
- Swagger UI и OpenAPI-документация.

## Локальный запуск

Инструкция ориентирована на Windows и PowerShell.

### Требования

- JDK 21;
- Docker Desktop с запущенным Docker Engine;
- Git.

Maven отдельно устанавливать не требуется: в сервисах используется Maven
Wrapper.

### 1. Подготовить переменные окружения

Из корня репозитория:

``` powershell
Copy-Item .env.example .env
```

Заполните `.env` локальными значениями. В частности, используются
настройки:

| Переменные                                                                     | Назначение                             |
|--------------------------------------------------------------------------------|----------------------------------------|
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`                            | PostgreSQL Main Backend                |
| `JWT_SECRET`                                                                   | Секрет для подписи JWT                 |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD`                                                | Необязательное создание администратора |
| `PAYMENTS_POSTGRES_DB`, `PAYMENTS_POSTGRES_USER`, `PAYMENTS_POSTGRES_PASSWORD` | PostgreSQL Payment Service             |
| `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`                                   | Подключение к Redis                    |
| `KAFKA_BOOTSTRAP_SERVERS`                                                      | Адрес Kafka                            |
| `KAFKA_APP_USERNAME`, `KAFKA_APP_PASSWORD`                                     | Учётные данные Kafka                   |
| `KAFKA_SSL_STORE_PASSWORD`                                                     | Пароль хранилища сертификатов          |
| `KAFKA_SSL_TRUSTSTORE_LOCATION`                                                | Путь к truststore                      |
| `PAYMENT_MOCK_FINAL_STATUS`                                                    | Итоговый статус mock-платежа           |

Для `JWT_SECRET` используйте случайное значение длиной не менее 32 байт.
Пароли и сертификаты должны быть локальными. Не коммитьте `.env`,
реальные credentials, keystore или truststore в Git.

Для локального Kafka-соединения также необходимо подготовить файлы
сертификатов и хранилищ в `kafka/secrets/`. Эти файлы намеренно не
включены в репозиторий.

### 2. Запустить инфраструктуру

Из корня репозитория:

``` powershell
docker compose up -d
docker compose ps
```

Docker Compose поднимает инфраструктуру, необходимую сервисам:
PostgreSQL, Redis и Kafka.

### 3. Создать Kafka topics

После запуска Kafka и подготовки локального truststore выполните из
корня репозитория:

``` powershell
.\kafka\init-topics.ps1
```

Скрипт читает настройки из `.env`, проверяет доступность контейнера
`skating-kafka`, подключается к Kafka по `SASL_SSL` и создаёт
отсутствующие топики.

### 4. Запустить Main Backend

В отдельном терминале:

``` powershell
cd backend/skating-platform-backend
.\mvnw.cmd spring-boot:run
```

При старте Liquibase применяет миграции базы данных.

Swagger UI:

``` text
http://localhost:8080/swagger-ui/index.html
```

OpenAPI JSON:

``` text
http://localhost:8080/v3/api-docs
```

### 5. Запустить Payment Service

В другом терминале:

``` powershell
cd backend/payment-service
.\mvnw.cmd spring-boot:run
```

Для локальной проверки платежей используется `MockPaymentGateway`.
Итоговый статус mock-платежа настраивается через
`PAYMENT_MOCK_FINAL_STATUS`.

При запуске приложений из IntelliJ IDEA убедитесь, что необходимые
переменные окружения переданы в Run Configuration. Наличие файла `.env`
в корне само по себе не гарантирует, что IntelliJ автоматически передаст
его значения Java-приложению.

## Конкурентность и надёжность

### Бронирование

При одновременной записи нескольких учеников на последнее свободное
место существует риск превысить вместимость занятия. В Main Backend эта
ситуация обрабатывается с помощью `PESSIMISTIC_WRITE`: запись о
тренировке блокируется на время транзакции, после чего проверяется
доступность мест и создаётся бронирование.

### Идемпотентность платежей

Повторная доставка Kafka-события или повторный запрос не должны
приводить к повторному созданию или применению одного и того же платежа.
Payment Service проверяет ключ идемпотентности и использует
согласованные операции с базой данных для защиты от конкурентной
обработки.

Main Backend также учитывает повторные и устаревшие события результата
оплаты, чтобы не применять один и тот же результат повторно и не
перезаписывать более актуальное состояние бронирования устаревшим
событием.

### Transactional Outbox

Оба сервиса используют outbox для публикации событий. Событие сначала
сохраняется в той же базе данных, что и бизнес-изменение, а затем
отдельный publisher отправляет его в Kafka. Это позволяет не связывать
фиксацию бизнес-транзакции с доступностью брокера в момент выполнения
запроса.

## CI

GitHub Actions настроен в `.github/workflows/backend-ci.yml`.

Workflow содержит отдельные проверки для:

- Main Backend — сборка и тесты;
- Payment Service — сборка и тесты.

Проверки запускаются при push и Pull Request в соответствии с
настройками workflow. Последний объединённый Pull Request с интеграцией
Payment Service и обновлением инфраструктуры прошёл все проверки CI.
